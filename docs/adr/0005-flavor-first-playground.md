# The playground ships one directory per flavor and stack

The playground's examples are grouped flavor-first: `playground/<flavor>/<stack>`, one self-contained directory per pair, for the three flavors `eslint`, `oxlint` and `eslint-oxlint` and the seven stacks the matrix covers. Each directory is a copy-pasteable consumer snapshot — its own manifest, linter config modules, project file and source tree, plus an `options.ts` in the paired flavor — and the playground index is a Flavor × Stack matrix whose cells link them. The registry discovers a pair by the directories that exist, so the layout, not a list, is the registration: `listStacks`, `listExamples`, `resolveStack` and the flavor-qualified `resolveExample` are the whole public surface, and an unknown example name lists only flavor-qualified names because one stack is three examples.

What a flavor may change inside a stack is deliberately small and is asserted rather than trusted:

- the linter config modules — `eslint.config.js` only, `oxlint.config.ts` only, or both;
- the options themselves — the paired flavor keeps them in `options.ts` because its two configs read one object, while a single-tool flavor writes them inline where it calls its one factory, as a project that runs one tool does; the ESLint-only flavor therefore states no `oxlint` entry at all;
- the declared dependencies — the shared set plus that flavor's tool packages (`eslint` and the ESLint plugin Bundle, or `oxlint` and the Oxlint plugin Bundle), while the peers the stack's Modules require stay in all three because Source's peer check runs for both Adapters;
- the README.

Everything else — the source tree, the project file, the stack's config files, the ignore and override entries of the options module, a monorepo example's nested package sources — is byte-identical across a stack's three directories. `test/examples/layout.test.ts` is the filesystem invariant that says so.

**One deliberate exception to "moved, not rewritten".** `playground/eslint-oxlint/ts-monorepo/options.ts` narrowed its `overrides` scope from `packages/core/**` to `packages/core/**/*.ts` (ticket #36). The bare glob also covered `packages/core/package.json`, where nothing but the Bridge turned the type-aware rule block off; an ESLint-only flavor ships no Bridge, so it died on a file no parser project covers. The narrowed scope belongs to the stack's options module rather than to the linter, so all three flavors carry it and the existing example now demonstrates it in every flavor.

**The Bridge is not a flavor difference.** It is enabled by the `oxlint` entry of the stack's options module, and five of the seven stacks leave that entry unset on purpose, so their paired ESLint Emission carries no Bridge at all. The paired flavor is the example that already existed, moved rather than rewritten apart from the one exception recorded above: no stack gains an `oxlint` entry to make its pairing look uniform, because that would change the Emission the example exists to show. The contract is therefore a relation, not a list: the paired ESLint Emission equals the ESLint flavor's Emission plus the Bridge tail, the tail is empty exactly when the options module has no `oxlint` entry, and the Oxlint flavor's Oxlint Emission always equals the paired flavor's.

Terms are defined in [GLOSSARY.md](../../GLOSSARY.md); the Bridge rule this layout defers to is [ADR 0004](0004-oxlint-bridge-closes-the-emission.md), and the Adapter split that lets one options module feed two tools is [ADR 0001](0001-source-and-composers.md).

## Considered Options

- **A shared source tree via symlinks.** One directory per stack could hold the source, project file and stack config files, with each flavor directory symlinking them. It would remove the duplication and would make drift impossible. It would also stop the snapshot from being a snapshot: a reader who copies or archives an example directory gets dangling links, the copies are no longer portable across filesystems or archives, and the "differ only in the linter" contract becomes invisible because the diff of two directories no longer shows which files they share. The three directories exist so that a diff between them is the flavor, and a symlinked tree hides exactly that.
- **A generator step.** One source tree plus a script materializing the three flavor directories would keep a single authoring location. A generated tree still has to be committed to be reviewable, so the twenty-one directories remain and a generator is added on top — with its own maintenance, its own failure mode, and a review diff that mixes generated churn with hand edits. If it were generated on demand instead, the playground would stop being executable documentation: cloning the repository would no longer be enough to read or run an example.
- **One README per stack, living outside the examples.** The canonical stack README — predecessor mapping, options table, tree, installation caveats — could live in the playground index or in `docs/`, once per stack. Readers copy directories, though, and a mapping that lives elsewhere is lost at exactly the moment it is needed; it also splits stack knowledge from the snapshot it describes and invites dead links whenever a directory moves. The first implementation kept one canonical README in the paired flavor, with the two single-tool READMEs stripping and linking back; the update below replaced that with stubs.

## Update: the READMEs are stubs

The per-example READMEs began as stack essays — predecessor config, options table, rule mapping, installation caveats — with the paired flavor canonical. The documentation cleanup removed them: a paired README now names the project the stack stands in for, a single-tool README names its flavor, and the options and config modules beside them are what a reader copies. The essays duplicated those files and the index row, and they were the part that went stale first; the index's Simulates column keeps the one-line mapping.

## Consequences

- **Accepted risk: twenty-one mostly-identical snapshots.** That is a lot of files for a consumer-layout change, and hand-maintained copies drift. The mitigation is the filesystem invariant spec: `test/examples/layout.test.ts` compares each stack's file sets and then every shared file byte for byte, and `test/examples/flavors.test.ts` relates the three Emissions, so drift is a failing suite rather than a review responsibility. A stack that loses a directory also fails, because the flavor contract asserts three flavors per stack rather than accepting the ones present — the migration's temporary "flat directory is the paired flavor" fallback is gone.
- The registry keeps no compatibility alias for the old flat names. A bare stack name is a stack, which the runner expands into its three flavors; the registry only resolves `<flavor>/<stack>`, and its unknown-name failure lists only flavor-qualified names. The runner's unknown-stack failure lists stack names. That is ticket #37's single-vocabulary reading, which superseded the spec's user story 14 asking an unknown name to list both the stacks and the flavor-qualified names: a message that mixed the two vocabularies would suggest a bare stack name is an example.
- Repository plumbing learns one shape: the workspace declaration, the unused-dependency mapping, the task input groups, the root project includes and the repository's own lint ignores all name two-level globs, never a per-example entry. Adding a stack is adding three directories. The root TypeScript project includes each example's `uno.config.ts` and `vite.config.ts` because an Oxlint-only flavor ships no example ESLint config module for ESLint's config lookup to find, so the root config is what lints those files — plumbing, not a flavor difference.
- The documentation surface is the index, this record, the glossary's **Flavor** and **Stack**, and the per-example README stubs. Every relative Markdown link under `playground/` is resolved by `test/playground-links.test.ts`, because the migration left twenty-two links pointing at directories that had moved and nothing caught it; the matrix adds twenty-one more.
